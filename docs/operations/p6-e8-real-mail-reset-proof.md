# P6 E8 — recorded real-mail password-reset proof (AUTH4-aware plan; nothing executed)

**Status: DESIGN ONLY.** This document authorizes nothing. Every step below that touches
AWS, DNS, a deployment, a mailbox or a live environment needs its own written authorization
naming this document. `E8_COMPLETE = false` until the recorded run described here has
happened in the authorized live environment (staging) and its evidence set is sealed.

**Governing criterion** (`docs/project-phase-6-plan.md` §19, item 8): *"A password reset has
been completed end to end by a user who did not know their password"* — and *"E8 requires a
recorded real-mail reset, end to end, in an authorized live environment under 6B-4C"*
(founder decision FD-13, 2026-09-26). Tests through the in-memory sender, the SES adapter
against a stubbed client, the development console sink, or the MSW-modelled API do **not**
satisfy it.

**Lineage.** This is the 18-step design from the sealed 6B-4C discovery evidence set
(`P6-6B4C-discovery/E8-PROOF-PLAN.txt`, 2026-09-27, code facts at main `584ca0c`), brought
onto `main` and updated for the changes merged since: **P6-AUTH-4** (#188 — server-side
sessions; the first workload start is now the one-way cutover), **P6-AUTH-5** (#190 — API
security headers; the SPA's build-time CSP allows exactly the API origin it was compiled
with) and the new Alembic head. Placeholders are used throughout: `<web-origin>` (the SPA
origin, `https://` + the SPA FQDN), `<api-origin>` (`https://` + the API hostname),
`<sending-domain>` (the SES domain identity), `<from-address>` (the bare From address).
**No real hostname, address or account identifier is written into this repository**; the
operator's chosen values live in git-ignored tfvars and in the sealed decision record.

## 1. Steps (API calls use `curl -is`, never `-v`; secrets live only in shell variables)

1. **Establish the account.** UI `<web-origin>/register` with M1 and a strong initial password. Expect 201. Receipt: status, `user.id`, masked M1 (`u***@domain`). Never the password.
2. **Sign in.** `POST <api-origin>/api/v1/auth/login` → 200. Receipt: status, `user.id`, `email_verified=false`. Keep the access token only in a shell variable.
3. **Pre-reset authorization.** Decode the login JWT locally and record ONLY `iat`, `exp`, `auth_epoch` (int), `sub` (own UUID) and the *presence* of a `sid` claim (AUTH4 — 32 lowercase hex; record presence, never the value). Never the token or any hash of it.
4. **Request the reset.** `POST <api-origin>/api/v1/auth/password-reset/request` with M1 → expect 204, empty body. Receipt: status, timestamp, `x-request-id`, sorted header-NAME list, sha256 of the (empty) body.
5. **Anti-enumeration, known address.** The step-4 receipt is the known-address half of the step-16 comparison. Log receipt: `security.password_reset.requested outcome=issued`.
6. **Receive real mail in M1** (check spam too). View the raw source locally; do not save it into evidence. Receipt: From (`<from-address>`, display name "SignalNest"), masked To, received timestamp, Subject `Reset your SignalNest password`, the SES `Message-ID` header.
7. **Correlate.** The SES Message-ID local part == `provider_message_id` in the API's `mail.sent` event (`outcome=success`, `template=password_reset`, `backend=ses`). Receipt: "correlated: yes", the message id, SES region.
8. **Link check BEFORE clicking:** origin == `<web-origin>` exactly, path `/reset-password`, token after `#token=`, no `?`. Receipt: three yes/no answers only. Never the URL or token.
9. **Open the real link in a real browser.** Expect the new-password form, and an address bar with no `#token=` after load (scrubbed by the SPA). Receipt: textual note; a screenshot only if it shows no URL.
10. **Set a new password** (different, strong). Expect redirect to `/sign-in` with the reset notice. Receipt: notice text seen; log `security.password_reset.completed outcome=success`.
11. **No auto-login (FD-9):** at `/sign-in`, no app content, auth token key absent in `localStorage`. Receipt: yes/no.
12. **Old password:** login with the old password → expect 401. Receipt: status only.
13. **New password:** login with the new password → expect 200; `email_verified=true` (FD-7 side effect). Receipt: status, same `user.id`, `email_verified=true`.
14. **Pre-reset JWT (AUTH4-aware wording).** `GET <api-origin>/api/v1/auth/me` with the step-2 token → expect 401. Receipt: status plus the statement: *"rejected because the token's `auth_epoch` (step 3) no longer equals the account's `auth_epoch`, incremented atomically with the password update (`app/auth/account_tokens.py`, `confirm_password_reset`). Under P6-AUTH-4 every request also requires a live `auth_sessions` row for the token's `sid`; the reset does not revoke session rows itself — the epoch mismatch refuses every token issued before the reset, on every device, and the session check remains in force for tokens issued after it."* Then unset the variable. (The 2026-09-27 text "P6-AUTH-4 remains OPEN" is superseded: AUTH4 closed in #188.)
15. **Replay.** Open the SAME email link again in a fresh private window; submit a VALID new password (bounds are checked before the token lookup, so an invalid password would not test replay). Expect the SPA's invalid-link panel backed by `404 password_reset_invalid`. Receipt: UI state + the API `http.request` log line (path `/api/v1/auth/password-reset/confirm`, status 404). The token never leaves the email. Then: sign in with the new password still works.
16. **Unknown address.** The step-4 request with M2 (never registered) → expect 204, empty body. Receipt: body sha256 equal to step 4, sorted header-NAME sets equal (values such as `Date` and `x-request-id` excluded). State explicitly: response-shape indistinguishability only; timing is NOT equalized (self-disclosed residual).
17. **No mail for M2.** Primary evidence: the API log shows `security.password_reset.requested outcome=suppressed` for the step-16 request and ZERO `mail.sent` / `mail.send_failed` events from that request time to +5 min (the suppressed path schedules no background task at all). Supplementary: the operator attests M2 inbox + spam received nothing from `<from-address>` for 90 min. If sandboxed, M2 is unverified, so a wrongful send would be refused by SES and would still appear as `mail.send_failed`; the log evidence remains probative and the inbox attestation is recorded as non-probative.
18. **Leak scan** (no raw secret needs to be stored to prove absence): pull the API logs for the step 1–17 window into a TEMPORARY file outside evidence; scan for candidate raw tokens (`[A-Za-z0-9_-]{43,}` excluding hex digests), JWTs (`eyJ…\.…\.`), bcrypt (`$2[aby]$`), `Authorization: Bearer`, `#token=`; while the old and new passwords are still in shell variables, `grep -rF` both over logs and evidence → zero hits; then unset every variable and delete the temporary file. Run the same scans over the evidence directory before sealing. Receipt: pattern list, hit counts (expected 0), timestamp. Never the matched text.

**Abort criteria.** Any expected result not met → stop, record, do not retry beyond pacing. `mail.send_failed` with `error_class=provider_error` on the first send → stop: likely IAM (an `AccessDenied` collapses to `provider_error`) or a `ses:FromAddress` mismatch — investigate read-only before retrying. Any secret observed in a log or evidence file → stop, contain, rotate as needed, record the incident without the value.

**Cleanup.** The test account may remain (operator-owned). Record whether it was deactivated. No data rollback.

## 2. Evidence hygiene (binding for the run's evidence set)

MUST NOT appear anywhere in evidence: passwords; raw reset or verification tokens; the token-bearing link or any URL containing `#token=`; `Authorization` headers; JWTs (not even truncated); hashes of tokens or JWTs; AWS credentials; full raw email source or token-bearing bodies; `curl -v` output of authenticated or confirm calls; unmasked recipient addresses in any IAM or SES read-back. MAY appear: SES MessageId / `provider_message_id`; `x-request-id`; timestamps; HTTP status codes; `error.code` values; masked recipient (`u***@domain`); the sender address; the subject; the SES region; commit SHA; image digests; task-definition / service revisions; the JWT claims `iat`, `exp`, `auth_epoch`, `sub` (own test UUID) and `sid` *presence*.

## 3. Supplement (recommended, not required): live verification mail

Same preconditions and hygiene. Use a separate fresh account (M3), because the E8 reset marks M1 verified (FD-7). V1 register and sign in (banner visible) · V2 "Send verification email" → 204; log `security.email_verification.requested outcome=issued`, `mail.sent template=email_verification` · V3 receive; correlate Message-ID · V4 link check (`/verify-email`, token in the fragment) · V5 same-account requirement (FD-10): signed out → in-page sign-in with the token held in memory; a different account → `403 email_verification_wrong_account`, token not consumed · V6 explicit "Verify email" click → 204 · V7 `/auth/me` `email_verified=true`, banner gone · V8 replay → `404 email_verification_invalid` · V9 leak scan as in step 18.
